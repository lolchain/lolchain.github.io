## Analysis procedure

### Collect

IPFS peer/client configuration, process sockets and available application messages.

### Inspect

Determine whether the sample uses native peer messaging, content retrieval or both; preserve peer IDs and session context.

### Correlate

Relate peer traffic to host commands or results using application/endpoint evidence.

### Interpretation limits

HTTP gateway inventory does not cover native peer traffic. A peer connection alone does not reveal message contents or attacker control.

Methods: [IPFS, IPNS and Arweave](content.md).

## Catalog context

Intezer documents cross-platform IPStorm variants using IPFS to conceal botnet communications. This extends beyond public HTTP gateways.

Examples: IPStorm

### Detection guidance

Look for unexpected peer networking, new long-lived sessions and unknown executables. Gateway-only detections are incomplete.

### Defensive approach

Use endpoint visibility and egress application controls; identify unauthorized peer clients and persistence.

## ATT&CK assessment

Enterprise · Tactic only · Reported behavior

IPStorm uses a peer overlay for C2. The catalog does not establish a precise ATT&CK transport technique; peer-to-peer routing alone is not automatically Non-Application Layer Protocol.
