# LBC-005 · Bitcoin OP_RETURN dead drops

Evidence: **Observed** · Reviewed 2026-10-16
Chains: Bitcoin · Networks: Mainnet

Encrypted backup C2 domains are embedded in Bitcoin transactions.

## Analysis procedure

### Collect

Reference address, transaction history, raw transactions and sample OP_RETURN decoder.

### Inspect

Select the transaction/output exactly as the sample does; extract pushed bytes and reproduce the evidenced decryption.

### Correlate

Correlate the recovered backup domain with a later DNS/proxy/C2 event and the fallback trigger.

### Interpretation limits

A public reference address may not be attacker-owned. OP_RETURN transactions cannot enumerate readers or infected hosts.

Methods: [Bitcoin transaction channels](bitcoin.md).

## Catalog context

Glupteba recovers backup C2 domains from encrypted Bitcoin OP_RETURN data. Google documents disruption; earlier Trend Micro analysis describes Electrum queries for transaction history. Explorer APIs and Electrum servers are different retrieval paths. Chainalysis reports a suspected Iran-nexus OP_RETURN resolver using a public reference address; that reference is not attacker-owned.

Examples: Glupteba; suspected Iran-nexus operator reported by Chainalysis

### Detection guidance

Look for transaction lookups from unexpected processes followed by new HTTPS destinations, especially after C2 failures. Differentiate the transaction sender, reference recipient and OP_RETURN contents; a public reference recipient is not an attribution verdict.

### Defensive approach

Monitor explorer APIs and Bitcoin clients; hunt wallet strings in samples. Revalidate historical domains before blocking.

## ATT&CK assessment

Enterprise · Technique · Reported behavior

OP_RETURN contains a pointer to an off-chain C2 domain, used when primary servers fail. This supports both dead-drop resolution and a fallback channel.

- [TA0011 · Command and Control](https://attack.mitre.org/tactics/TA0011/)
