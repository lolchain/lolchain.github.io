# LBC-032 · Blockchain fallback in multi-channel bootstrapping

Evidence: **Implemented** · Reviewed 2026-10-15
Chains: Ethereum, IPFS · Networks: Mainnet

An implant bundles chain and distributed-storage recovery alongside conventional channels.

## Analysis procedure

### Collect

Multi-channel loader configuration, IPFS stage, Ethereum branch and module enable/disable state.

### Inspect

Map fallback conditions and determine which route ran from captured requests; inspect IPFS and EVM evidence separately.

### Correlate

Tie enabled behavior to payload and process artifacts; mark disabled collection/propagation features as code-only.

### Interpretation limits

Ethereum configuration is not a confirmed command exchange. Do not report disabled exfiltration modules as observed data loss.

Methods: [EVM contracts and transaction data](evm.md), [IPFS, IPNS and Arweave](content.md).

## Catalog context

AsyncAPI reports establish IPFS staging and Ethereum configuration in a multi-channel loader. A configured Ethereum route is not proof of an observed command exchange. Microsoft states that credential harvesting, encrypted exfiltration and propagation modules were disabled in the analyzed build.

Examples: AsyncAPI / Miasma; Ethereum exchange unconfirmed

### Detection guidance

Separate active IPFS requests from fallback configuration discovered in files. Correlate CI/package import activity with interpreter egress.

### Defensive approach

Remove affected releases and investigate execution. Cover fallback surfaces using approved application policy without treating disabled modules as observed exfiltration.
