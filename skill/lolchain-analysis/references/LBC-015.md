## Analysis procedure

### Collect

NKN client identity, seed discovery, selected relay and malware message-handling code.

### Inspect

Separate discovery, relay sessions and NKN messaging from wallet transactions; preserve encrypted message envelopes if available.

### Correlate

Link incoming messages to commands and host behavior; keep MQTT or other parallel channels distinct.

### Interpretation limits

A relay is not automatically attacker-owned. Ledger history cannot reconstruct off-chain NKN message contents.

Methods: [NKN and TON transport](overlays.md).

## Catalog context

Malware uses NKN seed discovery and peer messaging for control. AhnLab publishes NKNShell seed traffic and the returned relay. NKNShell also supports MQTT, which is a separate non-blockchain channel. A relay carrying a session is not thereby attacker-owned.

Examples: NGLite; NKAbuse; NKNShell

### Detection guidance

Hunt unexpected NKN client processes and seed access, then correlate subsequent peer connections.

### Defensive approach

Restrict unauthorized NKN use by application and egress policy. Do not classify relay peers as attacker-owned merely from transit.

## ATT&CK assessment

Enterprise · Tactic only · Reported behavior

NKN relays commands through a shared peer overlay. This supports the C2 tactic, but does not by itself justify a Web Service or Non-Application Layer Protocol technique.

- [TA0011 · Command and Control](https://attack.mitre.org/tactics/TA0011/)
