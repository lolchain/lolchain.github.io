# LBC-002 · Transaction calldata as a payload store

Evidence: **Observed** · Reviewed 2026-10-16
Chains: Ethereum, BNB Smart Chain · Networks: Mainnet

Malware retrieves encoded payloads from transaction input data rather than a file server.

## Analysis procedure

### Collect

Transaction hash/history API response, input field and the loader’s selection rule.

### Inspect

Retrieve the selected transaction input; retain destination, status, block and exact byte offsets before decoding.

### Correlate

Connect the decoded instructions or configuration to the next stage and the loader’s actual history ordering.

### Interpretation limits

Do not confuse calldata with getter return data. A transaction to a burn address does not establish contract execution.

Methods: [EVM contracts and transaction data](evm.md).

## Catalog context

GTIG describes BSC contract staging followed by Ethereum transaction-history reads, including transactions to a burn address. Explorer APIs return the payload data. Chainalysis also covers BSC input-data stages reached through TRON/Aptos.

Examples: UNC5342 / JADESNOW / INVISIBLEFERRET

### Detection guidance

Hunt unusual transaction-history API access followed by in-memory execution. Capture transaction hashes as well as domains.

### Defensive approach

Use API-aware egress monitoring. A burn address is not a network endpoint; block the retrieval path or identified payload infrastructure.

## ATT&CK assessment

Enterprise · Technique · Reported behavior

Storing payload code in transaction input is malware staging; a downloader retrieving that code transfers a tool into the victim environment. Payload storage alone is not a C2-address dead drop.

- [TA0042 · Resource Development](https://attack.mitre.org/tactics/TA0042/)
