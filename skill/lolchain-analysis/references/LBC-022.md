# LBC-022 · Solana memo dead-drop resolution

Transaction memos publish rotating next-stage configuration.

## Analysis procedure

### Collect

Wallet, cluster, getSignaturesForAddress/getTransaction responses and loader memo-selection rule.

### Inspect

Page history to the incident window, inspect transaction status/instructions and decode the selected memo.

### Correlate

Match the next-stage URL/content to the loader’s request and later execution or collection events.

### Interpretation limits

Address references need not be signatures by that address. A configured fallback route is not a confirmed session.

Methods: [Solana memo resolution](solana.md).

## Catalog context

Loaders read Solana transaction memos for next-stage configuration. Primary reports document IDE, npm and Python repository delivery contexts. RPC fallback lists are code evidence; a controlled run may contact only one provider. Payload and file exfiltration can use separate HTTP servers.

Examples: GlassWorm-linked extensions; npm loaders; ForceMemo

### Detection guidance

Correlate IDE or Node.js blockchain access with remote code retrieval, local collection and new outbound destinations.

### Defensive approach

Review extension provenance, restrict unsanctioned RPC traffic and rotate credentials exposed by confirmed malicious extensions.

## ATT&CK assessment

Enterprise · Technique · Reported behavior

Solana memos resolve next-stage configuration, followed by remote-code retrieval. MITRE also lists GlassWorm under Dead Drop Resolver. The reported HTTP exfiltration is outside this memo-resolution mapping.

- [TA0011 · Command and Control](https://attack.mitre.org/tactics/TA0011/)
- [T1102.001 · Web Service: Dead Drop Resolver](https://attack.mitre.org/techniques/T1102/001/)
